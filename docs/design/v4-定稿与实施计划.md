# DSH 助理 Profile 设计

## 1. 定位

本项目提供可复用的 DeepSeek Harness 聊天助理 profile。
DSH 提供模型、工具、会话、调度和权限能力，本项目提供聊天通道、消息治理、身份装配和启动管理。
助理进程不监听入站端口，通过 Telegram Bot API 长轮询收发消息。

## 2. 支持基线

接口基线为 DSH npm `0.2.2-rc.1`。宿主接口和源码位置见
[DSH 接口契约](../notes/dsh-api-contract.md)。代码使用 ESM JavaScript 与 JSDoc，运行时仅使用 Node.js 内建模块和本项目包。

## 3. 交付组成

| 组件 | 职责 |
|---|---|
| `@junjiangao/assistant-bundle` | 组合补丁和生成的 standard preset |
| `@junjiangao/channel-core` | 路由、收据、账本、限速、问答与审批桥接 |
| `@junjiangao/channel-telegram` | Telegram 协议归一化和传输 |
| `@junjiangao/assistant-startup` | 三种启动模式、身份装配和诊断 |

包通过本地 `file:` 依赖组合，保持 `private: true`。

## 4. Profile 与补丁

`assistant` profile 按顺序加载 `@deepseek-ai/dsh-base`、`@deepseek-ai/dsh-web-app`、
`@junjiangao/assistant-bundle`。profile 的用户补丁在 bundle 之后应用；项目配置不写到影响所有 profile 的数据根补丁中。

### 4.2 表现层裁剪

bundle 禁用 Web 服务、Web 启动、浏览器/桌面 UI 和相关遥测表现层行。
禁用名单由生成器与上游行清单核对。

### 4.3 功能层保留

保留会话控制、预设、文件上传服务、工作区、凭据、调度等依赖。
`connection` 重新声明为无 `webStartup` 注入，以便会话控制在没有 Web 监听时仍能就绪。
插件行的 `disabled: !!js` 只读取全局对象；服务注入尚未完成时不能访问 `ctx` 服务。

### 4.4 Standard preset

生成器读取匹配版本的上游 preset，恰好完成三处修改：移除 persona、提问改为 timed/600、禁用模型插件管理工具。
生成文件与上游许可声明一并保存在 bundle 中。升级后重新生成并核对差异。

## 5. 身份与工作区

`assistant-startup` 读取数据根中的 `identity/SOUL.md` 和 `identity/SYSTEM.md`，注册独立 prompt section，
分别使用 order 0 和 10200，且 `interpolate: false`。`AGENTS.md` 使用 DSH 原生指令链。
模板由部署者定制；身份内容的行为约定不替代 DSH 的权限执行。
启动前快照及差异通知用于身份变更追踪。

## 6. 权限

继承 DSH 的 `workspace-write + ask`，环境变量示例显式设置 `DSH_PERMISSION_MODE=workspace-write`。
扩大单次操作权限时，由 DSH 的 `approval/request` 请求已绑定聊天的 owner 决定。
完整访问仅在部署者显式设置 `DSH_PERMISSION_MODE=danger-full-access` 时启用。
既有会话保留 DSH 已持久化的策略，不因默认值变化而自动迁移。

文件写入约束由 DSH 的执行后端实现，其效果依赖操作系统和实际后端；profile 不提供整机隔离。
应使用专用非 root 运行用户并按部署环境管理主机权限。真实凭据只保存在受限的环境文件或 DSH 凭据机制中。

## 7. 通道核心

### 7.1 适配器契约

适配器提交 `InboundEvent`，core 提供 `ChannelHost`，通过 send/edit/probe 等方法出站。
`host.ingest(event, { prepareAttachments })` 的可选准备回调仅在收据去重和 owner 检查通过后调用。

### 7.2 入站

收据去重 → owner 检查 → 附件准备 → 命令/审批/问答处理 → 路由 → 内容提交 → 收据与游标结算。
未授权事件只结算和留痕；临时提交失败保留游标以便重投。请求 id 用于 DSH 提交幂等。

### 7.3 出站

按路由和回合维护流式消息、分条终稿与投递账本。限速队列处理出站节奏和 429 重排。
重复终止事件不会重复投递终稿。崩溃恢复只封口和补中断提示，不重放工具副作用。
没有聊天绑定的会话输出记为未投递，不自动转发到其他聊天。

### 7.4 提问与审批

普通问题通过 `user-questions/request` 接入；带有效 callId 的超时问题可按 DSH 契约补答。
审批单独监听 `approval/request`，待办仅在内存中保存，绑定原会话和聊天/话题；回调数据使用独立随机标识并限制在平台长度内。
白名单 owner 通过按钮允许一次或拒绝，等待上限 600 秒。取消、超时、退出和重启后请求失效。
`/skip` 拒绝当前聊天的审批，并保留普通问题跳过行为；`/stop` 通过 DSH 取消回合。
DSH 持久化审批请求及决定，桥接器不恢复旧授权。

### 7.5 命令

通道命令管理路由、会话和状态；`/compact`、`/goal` 转发 DSH 命令。
`/model` 切换同时影响宿主默认模型；`/preset` 在首轮后需要通过 `/new` 更换。

## 8. Telegram 呈现

General 话题的发送与 typing 参数按平台差异分别处理。
长回复分条，工具状态从持久会话事件取得；附件在授权后落盘，交付物由 present 事件发送。
`apiBase` 是部署级可信配置，默认官方 HTTPS 地址。携带 token 的请求拒绝自动重定向，诊断清理认证字段。

## 9. 启动与运维

### 9.2 网络

本项目禁用入站 Web 服务，外部接入使用出站长轮询。主机服务与防火墙由部署者管理。

### 9.3 诊断与健康

`--doctor` 读取状态并探测已配置通道；shell 包装补充模型配置和监听检查。
健康 timer 根据心跳和进程状态重启服务，身份快照在主服务启动前执行。

### 9.4 崩溃与互斥

同一数据根仅允许一个 daemon 持锁。状态采用原子写盘；恢复不重放副作用。

### 9.5 生命周期

插件通过 context disposer 释放计时器和等待项，退出与信号由 DSH 启动器管理。

### 9.6 模式

- daemon：启用聊天、调度、心跳与单实例锁。
- `--once`：执行一次回合，不启用聊天与调度，也不抢 daemon 锁。
- `--doctor`：诊断模式，不启动聊天循环。

无聊天路由或 `--once` 中没有可用应答方时，DSH 拒绝需要审批的操作。

### 9.7 升级

安装匹配版本、运行 `pnpm verify`、重新生成并查看 preset 差异，再按部署安排更新运行实例。
`--check --strict` 用于要求禁用名单全命中；同版本 npm 与桌面构建的已知行差异见接口契约。

## 10. 数据布局

数据根包含身份、会话、storages、channels、run、audit、logs 和 workspace。
owner 白名单、话题角色、网关及凭据属于部署配置，不固化到源码。
通道审计记录消息和投递生命周期；工具与审批历史由 DSH 的会话机制负责。

## 11. 验证

自动化检查使用 `pnpm verify`；真实环境验证缺口集中记录在
